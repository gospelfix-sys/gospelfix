사용자에게 "이 기능을 만들면 결과가 어떻게 나오나요" 류의 질문을 받으면, 파일
경로·데이터 스키마·아키텍처를 앞세운 기술적 설명보다 **실제 화면에 무엇이 보이고
무엇을 받게 되는지**를 평이한 언어로 먼저 보여준다.

**Why:** "상품 상세페이지 차별화" 기능을 설명할 때 처음에는 `ProductInfoChips.tsx`
위치, `content_api_configs` 스키마, cms.api 마이그레이션 절차부터 설명했더니 사용자가
"나 잘 이해가 안되네 결과물이 어떻게 나온다는거야?"라고 되물었다. 이후 상세페이지
before/after ASCII 목업("정보 칩에 이 줄이 하나 더 생긴다", "다운로드 버튼이 하나 더
생긴다")으로 다시 설명하니 바로 이해하고 "오케이 이대로 진행해줘"로 진행 승인이
나왔다.

**How to apply:** "이게 뭐야", "결과물이 어떻게 나와" 같은 질문에는 먼저 화면
목업/전후 비교부터 제시하고, 파일 경로나 스키마 같은 구현 디테일은 사용자가 "어떻게
구현하는지"를 물을 때만 이어서 설명한다. 이미 기술적으로 설명한 뒤 사용자가 이해를
못했다는 신호를 주면, 같은 내용을 더 자세히 반복하지 말고 형식 자체를 목업/비유
중심으로 바꿀 것.
