새 기능 요청에 "이걸 완전히 새로운 카테고리/상품 유형으로 만들자"는 설계를 먼저 제안하지
않는다. 코드베이스 조사로 제약(예: 결제 인프라 한계, SKU 1:1 구조)을 근거로 정교한 신규
설계를 제시해도, 사용자는 결국 기존 UI 요소를 조금만 확장하는 훨씬 단순한 방향을
선택했다.

**Why:** [[project_prompt_sale_category_attempt_reverted]] 사례. "프롬프트 파일 별도
판매"를 위해 `prompt`라는 새 카테고리를 신설하고 gospelfix+cms.api 양쪽에 조건부 로직을
추가하는 설계를 code-reviewer 승인까지 받아 구현했다. 그런데 실제 관리자 화면에서 확인한
사용자는 "기존과 다를 게 없다"고 느꼈고, 결국 "카테고리는 필요 없다. 그냥 기존 코드
미리보기 섹션을 무료/유료 상관없이 보이게만 해달라"로 요구를 단순화했다. 처음 설계가
"틀린" 건 아니었지만(리뷰도 통과했고 기술적으로 정확했음), 사용자가 실제로 원한 것보다
과했다.

**How to apply:** 비즈니스 요구사항이 애매하거나 사용자가 "이런 것도 되면 좋겠다" 식으로
가볍게 던진 아이디어일 때는, 새 개념(카테고리, 상품 타입, 새 테이블/필드)을 만드는 방향과
기존 요소를 확장하는 방향 두 가지를 제안 초반에 함께 제시하고 어느 쪽을 원하는지 먼저
확인하는 게 낫다. 조사 결과 복잡한 제약이 발견되더라도, 그게 "복잡한 설계가 필요하다"는
뜻은 아니고 "단순한 방향으로 가되 이런 제약이 있다는 걸 알아두자" 정도로 받아들여질
수 있다는 걸 감안할 것.
